# Постоянные инструкции Codex: Podkop Rules

## Назначение и границы

Поддерживай независимые маршрутизируемые списки Telegram, Twitch, Albion Online, KinoPub и будущих сервисов. Пользователь может написать «Добавь Discord», «Добавь YouTube», «Добавь Steam», «Добавь ChatGPT», «Обнови Albion Online», «Проверь актуальность всех списков» или «Удали Twitch». Самостоятельно выполняй соответствующий процесс ниже, без повторного объяснения структуры пользователем.

Цель совместимости: Podkop 0.7.22, инфраструктура пользователя OpenWrt 25.12.5, VLESS Reality, sing-box. Не меняй роутер, VPN-сервер, outbound, DNS или sing-box-конфигурацию. Подготовка списков не равна проверке реального маршрута. Документация по-русски, код и идентификаторы по-английски. Списки сообщества Podkop не использовать.

Работай автономно в разрешённой области. Не спрашивай сведения, которые доступны в проекте и официальных источниках. Не выполняй разрушительные операции без подтверждения. Не выдавай предположения за факты и не публикуй неподтверждённые записи.

## Архитектура

- `services.json` — единственный реестр сервисов. Поля: `name` (название в таблице README), `enabled`, `domains`, `auto_update`, `sources`; `subnets` необязателен. ID соответствует `[a-z][a-z0-9_-]*`, кроме `all`; пути строго `domains/<id>.txt` и, при наличии, `subnets/<id>.txt`. Если IP-список не предусмотрен, поле `subnets` отсутствует (не `null`), файл не создаётся. Не создавай дублирующих ID.
- `sources/sources.json` — источники с ID, `service`, HTTPS URL, `data_type` (`domains`, `subnets`, `context`), `trust`, `method`, датами `last_checked`/`last_updated`, `auto_update`, `records`, `notes`. Для каждого опубликованного маршрута должен быть источник с точной записью в `records`. Даты ставь только по выполненной проверке. Для независимой официальной интеграции поясняй, что источник не принадлежит самому сервису.
- Пользовательские адреса по прямому запросу допускаются как `trust: user-supplied`, `method: user-input`, `auto_update: false`. Сохраняй ввод в `sources/manual/<id>.json`, указывай `input_file`. При отсутствии внешнего источника используй `url: null`, без независимой проверки — `last_checked: null`. Это происхождение пользовательского запроса, а не официальное подтверждение связи с сервисом. Не переименовывай такие источники в official без исследования.
- `domains/<id>.txt` и существующие `subnets/<id>.txt` — локальная последняя проверенная версия, включая вручную сопровождаемые сервисы. Для сервиса без IP-списка не создавай пустой файл или заготовку подсетей. Добавлять такой файл и поле в реестр можно только после отдельного явного запроса пользователя. Сборка, валидация и автообновление отсутствующий IP-список не создают. У Twitch сейчас только доменный файл; IP-список Albion добавлен по отдельному запросу пользователя как точные `/32` из захватов, а не как официальный перечень сетей.
- `domains/all.txt`, `subnets/all.txt` — только генерация из включённых сервисов. Никогда не копируй записи в них вручную. Отключённый сервис остаётся в реестре и проходит проверку, но не входит в общий список и не обновляется.
- `scripts/common.py` — общие форматы, схема и атомарная запись. Три CLI используют эти функции. Не создавай отдельный скрипт под каждый сервис без необходимости.
- `tests/` — unittest, стандартная библиотека. `docs/` — совместимость, настройка, диагностика, публикация и журнал проверок.

## Форматы и совместимость

Прежде чем менять совместимость, изучи официальный исходный код целевого tag и `docs/podkop-compatibility.md`. Не переноси возможности текущей документации на 0.7.22 без проверки.

Домен: один lowercase ASCII/Punycode hostname на строку, без протокола, URL-пути, wildcard, пробелов, комментариев, пустых строк и дубликатов. Сортировка лексикографическая, LF, финальный newline. Bare domain использует `domain_suffix` и покрывает поддомены. Полностью пустой файл — ноль байт.

CIDR: канонический IPv4, строгая проверка host bits. Plain-subnet импорт 0.7.22 и nft-набор только IPv4. IPv6 из Telegram feed разбирается, но исключается из публикации. Не добавляй IPv6 в списки, пока вся цепочка Podkop/nft/движок не подтверждена для новой явной цели. Не смешивай домены и CIDR.

Не включай приватные/специальные сети. IPv4-префиксы шире `/16` запрещены по умолчанию. По прямому пользовательскому запросу конкретные широкие сети сохраняются как точные исключения `services.<id>.broad_subnets`, с `user-supplied` источником и исходным вводом. Описывай затрагиваемый посторонний трафик; не утверждай исключительное владение этими сетями сервисом. Такое исключение уже есть у KinoPub: см. `docs/kinopub.md`. Остальные широкие сети остаются запрещены, автоисточникам исключения не передаются. Не укрупняй диапазоны. При импорте пользовательского списка можно удалить полностью вложенный CIDR, только если тест доказывает равенство IP-покрытия до и после; исходный ввод сохраняй. Внутри сервисных файлов пересечения отклоняются. В общей сборке разрешено убрать точный дубликат и CIDR, полностью покрытый другой включённой сетью, без слияния соседних сетей и с тестом равенства покрытия. В отдельных сервисных файлах сохраняй их собственные маршруты, чтобы отключение другого сервиса не потеряло нужный IP.

## Добавление сервиса

1. **Исследуй.** Найди официальные сайт, авторизацию, API, CDN, медиа, web/desktop/mobile endpoint, игровые сервера при наличии. Проверь TCP/UDP, прямые подключения по IP, IPv6 и внешние зависимости. Приоритет: официальная документация, API, официальный репозиторий, первичные технические материалы; случайные списки не источник истины. Сохраняй ссылки и выводы. Если источник недоступен, зафиксируй это; не ставь успешную дату.
2. **Обоснуй IP.** DNS A-ответ не доказывает принадлежность игровому серверу или исключительное использование адреса. ASN/WHOIS и CDN-провайдер не дают основания включить его целиком. Не выдумывай IP и не включай полный AWS/Cloudflare/Fastly/DDoS диапазон. Если IP-список не предусмотрен или достаточных данных нет, не создавай файл подсетей. При необходимости опиши сбор реальных соединений; сам файл добавляй только по отдельному запросу пользователя.
3. **Зарегистрируй.** Выбери уникальный ID, создай доменный файл и запись в `services.json`. `subnets/<id>.txt` и поле `subnets` добавляй только при явно запрошенном IP-списке. Не создавай пустые заглушки. `auto_update: true` допустим только при существующем проверенном машинном источнике и зарегистрированном целевом файле. Без него используй ручное сопровождение, даже если пожелание пользователя — автоматизация.
4. **Добавь происхождение.** Запиши в sources метаданные, точные подтверждённые `records`, назначение, ограничения и фактические даты. Контекст без адресов — `data_type: context`. Машинные источники сейчас поддерживают только `https-cidr` для `subnets`; новый тип парсера требует реализации и тестов общей архитектуры.
5. **Пересобери и проверь.** Выполни команды ниже, исправь ошибки. Убедись, что новый сервис автоматически обнаруживается, отключение исключает его из all.txt, а другие сервисы не изменились без необходимости.
6. **Документируй.** Обнови таблицу README с фактическими числами, Raw URL, метод обновления, покрытие/пробелы и диагностику. Не заявляй полное покрытие на основе только домена сайта.
7. **Публикуй в рамках разрешения.** Если пользователь разрешил публикацию и доступ есть, проверь remote/ветку/историю, создай commit и обычный push. При существующем удалённом содержимом сначала изучи его; не перезаписывай без подтверждения. Не используй force push и не удаляй ветки. Если публикация не разрешена/недоступна — оставь готовый локальный результат и точные команды.
8. **Отчитайся.** Сервис, числа доменов/CIDR, источники, изменённые файлы, выполненные тесты, реальные Raw URL или явно помеченные шаблоны и ограничения.

## Обновление существующего сервиса / проверка всех списков

Найди записи в реестре и sources. Проверь доступность и актуальность первичных источников, изучи новые данные. Добавляй только подтверждённые записи. Для удалений требуются достаточные основания устаревания; временная ошибка HTTP/DNS или исчезновение в частичном feed не доказательство.

Для машинных подсетей используй `update_lists.py`. Он сохраняет последние корректные записи, новые добавляет, исчезнувшие перечисляет в `removal_candidates`. При ошибке одного сервиса не уничтожай остальные. При ошибке источник не получает успешную дату. Не заменяй проверенный непустой список пустым.

Обнови источники, пересобери общие списки, выполни тесты, обнови README/журнал проверок и подготовь публикацию. Для команды «Проверь актуальность всех списков» исследуй также ручные домены Twitch/Albion: успешный запуск Telegram updater не означает проверку всех сервисов.

## Удаление сервиса

Удаляй только запрошенный сервис из реестра, существующие его файлы и связанные source IDs. Не предполагай наличие файла подсетей. Пересобери all.txt; обнови README, URL, числа и ограничения; выполни тесты и валидацию. Не меняй другие сервисы без необходимости. Подготовь публикацию согласно текущему разрешению пользователя.

## Особенности игр и звонков

Для игр исследуй региональные входы и игровые сессии отдельно, launcher/обновления, DDoS ingress, динамические IP и реальные TCP/UDP. Для Albion обязательны Americas, Asia и Europe. Подтверждённые имена входа не являются полным перечнем игровых серверов. Используй `docs/albion-network-analysis.md` для Resource Monitor/TCPView, PowerShell, Wireshark и OpenWrt tcpdump. Наблюдаемый IP может быть общим; не обещай эксклюзивное владение.

У Telegram домены и CIDR не гарантируют звонки: P2P-собеседник может находиться вне сетей сервиса. Проверка UDP/outbound и реальных клиентов — отдельная процедура; не меняй ради неё конфигурацию пользователя автоматически.

## Проверки перед завершением

```sh
python -m compileall -q scripts tests
python -m unittest discover -s tests -v
python scripts/build_lists.py
python scripts/validate_lists.py
python scripts/build_lists.py --check
git diff --check
```

Проверяй домены, CIDR, дубликаты, пересечения, схему реестра/источников, происхождение записей, пустые списки, disabled, новую регистрацию, ошибки feed/отсутствие интернета, атомарную замену и идемпотентность. При изменении workflow проверь YAML и actionlint, если доступен; серверный успех утверждай только по фактическому запуску GitHub Actions.

Сохраняй минимальные зависимости. Не добавляй секреты, VPN-ссылки, пароли, токены, приватные конфиги и pcap. Не исполняй удалённые скрипты, не используй `curl | bash`, не отключай TLS. Actions: read-only validation, write только update-job; при ошибках ничего не публиковать. Повторные запуски с теми же данными/датой не должны менять файлы.

Проверь статус Git и дифф перед commit. `.research/`, кэш и локальные отчёты не публикуются. Укажи реальные результаты и ограничения в `docs/verification.md`; не придумывай успешные тесты, публикацию, Raw-проверку или полное покрытие сервиса.
