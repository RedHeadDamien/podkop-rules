# Albion Europe: сравнение пользовательских захватов

Дата анализа: 11 ноября 2026 года. Исходные CSV прочитаны без изменения. В репозитории сохранены только наблюдаемые DNS-имена, DNS-сводки, номера пакетов и SHA-256 файлов: [sources/manual/albion.json](../sources/manual/albion.json). Полные захваты, локальные адреса компьютера, параметры VPN и ключи не копировались.

Серия была предложена с остановленным Podkop. В CSV нет достоверного состояния служб роутера; остановка не подтверждена отдельным журналом. В 111.csv обнаружено шесть входящих пакетов от старых FakeIP-адресов, не сопоставленных в этом захвате с Albion; это могут быть остаточные фоновые соединения. DNS-ответы для исследуемых серверов Albion в этой серии содержат реальные адреса.

Успешный тест 333 показывает работоспособность выбранного сервера/ключа через Happ в момент теста. Он не доказывает одинаковую обработку UDP в Happ и sing-box на роутере. Ключ не следует считать неработоспособным только из-за отказа входа через Podkop.

В обоих захватах с Happ виден зашифрованный TCP/TLS-туннель. Последующие DNS-запросы к нескольким игровым узлам Europe согласуются с сообщением пользователя об успешной игре. Удалённые UDP-партнёры внутри туннеля в этих CSV не видны; отсутствие открытого UDP на физическом интерфейсе не означает отсутствие UDP внутри VPN.

В предыдущей серии с Podkop сервер входа Europe разрешался в FakeIP и получал исходящие UDP-пакеты без ответов в захвате. Поэтому пропуски доменов — подтверждённый недостаток списка, но не доказанная единственная причина ошибки. Нужно проверить журналы обработки UDP/FakeIP, выбор outbound и совместимость транспортного поведения клиента/сервера. Эти CSV не локализуют место потери пакетов и не доказывают блокировку со стороны конкретного оператора.

## Обновление списка

В `domains/albion.txt` добавлены восемь точных DNS-имён из пользовательских захватов:

```text
albion1.battleye.com
battleye.becdn.net
cdn.battleye.com
live01-win-status.dc02.albion.zone
live02-win-status.sg.albion.zone
live03-win-01.ams.albion.zone
live03-win-status.ams.albion.zone
master1.battleye.com
```

Это три региональных статуса, CNAME входа Europe и зависимости BattlEye/CDN. Они оформлены как `user-supplied`, без независимого официального подтверждения и без автоматического обновления. Игровые имена вида `live03-win-12.ams.albiononline.com` уже покрываются существующим `albiononline.com`; перечислять каждый такой поддомен отдельно не требуется.

В итоге в Albion 12 доменов, в общем доменном файле — 56. После отдельного запроса пользователя также создан `subnets/albion.txt` с 17 точными IPv4 `/32`: три адреса региональных статусов, адрес входа Europe, четыре игровых узла Europe, семь адресов сайта/статуса/CDN и два адреса BattlEye/CDN. Для каждой записи в `sources/manual/albion.json` сохранены DNS-имя, номер пакета, файл и наличие открытого обмена с адресом.

Часть `/32` подтверждается только DNS успешного сеанса: внутри Happ игровой обмен зашифрован. Это пользовательские наблюдения, не доказательство выделенного владения, стабильности или полного покрытия всех регионов. IPv6, FakeIP, локальные адреса, DNS-резолверы и VPN-серверы в файл не включены. Гарантия исправления маршрутизации после обновления не даётся.

Четыре `/32` уже полностью покрыты включёнными сетями KinoPub и поэтому отсутствуют в `subnets/all.txt`, но сохраняются в сервисном файле Albion. При отключении KinoPub точные адреса автоматически войдут в общую сборку. Никаких сетей провайдеров из найденных IP не выводилось. Общий IP-файл содержит 59 CIDR с тем же объединённым покрытием всех включённых сервисных файлов; это проверено тестом.

## Следующая проверка

Описанная ниже проверка выполнена пользователем; результат и ограничение временной правки приведены в следующем разделе.

После загрузки обновлённого доменного списка в Podkop пользователь полностью закрывает Happ и Albion, очищает DNS-кэш Windows командой `Clear-DnsClientCache`, затем повторяет вход. Если ошибка остаётся, полезны версия sing-box и журнал сразу после попытки:

```sh
sing-box version
logread | grep -Ei 'sing-box|podkop|fakeip|udp|albion|5055' | tail -n 100
```

Команды читают состояние и журнал, конфигурацию не меняют. Перед передачей результатов удалите секреты, если они встретятся; полный VLESS URL и UUID не нужны. Исследование и изменение настроек роутера остаются отдельной задачей.

## Результат контрольного теста hijack-dns

11 ноября 2026 года пользователь сообщил: после обновления доменных/IP-списков Albion через Podkop всё ещё не работал. В журнале sing-box 1.12.17 повторялись `router: process DNS packet: unpack request: dns: overflowing header size`, `overflow unpacking uint32` и `400 Bad Request` для `. CLASS0 None`.

Пользователь вывел первые правила действующей конфигурации: общий `sniff` для `tproxy-in`/`dns-in`, за которым следовал `hijack-dns` с `protocol: dns` без ограничения по порту. Этот порядок и ошибки соответствуют известному механизму ложного распознавания Photon UDP как DNS: [первичный отчёт о воспроизведении](https://github.com/hiddify/hiddify-core/issues/151). Такое сообщение само по себе не доказывает принадлежность каждого ошибочного пакета Albion, но контрольный тест связывает отказ с этим правилом.

После отдельного согласования диагностического изменения пользователь сохранил резервную копию, проверил конфигурацию через `sing-box check`, добавил только `port: 53` к существующему правилу `hijack-dns` и перезапустил только sing-box. Итоговое правило:

```json
{
  "action": "hijack-dns",
  "protocol": "dns",
  "port": 53
}
```

Пользователь сообщил «всё завелось». В присланном фрагменте журнала после изменения прежних ошибок разбора DNS нет. Это подтверждает успешный диагностический тест в его окружении; продолжительная стабильность и все три игровых региона отдельно не проверены.

Одна оставшаяся строка журнала содержит таймаут TCP-подключения к VLESS-серверу при обращении к ChatGPT. Это другой тип ошибки, не сообщение о разборе игрового пакета как DNS; работоспособность всех остальных сервисов из данного теста не следует.

Правка временная: Podkop генерирует конфигурацию sing-box заново. Перезапуск Podkop, применение настроек или обновление могут убрать `port: 53`. DNS на нестандартных портах больше не перехватывается этим ограниченным правилом. Для постоянного исправления потребуется отдельно согласованное изменение генератора Podkop либо проверенная версия с устранением проблемы. Репозиторий списков не меняет конфигурацию роутера автоматически.
